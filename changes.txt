    fix(traceboard): serialize naive UTC datetimes with Z suffix
    
    Timestamps displayed as '3h ago' immediately after an edit. Root cause:
    the DB stores UTC as naive datetimes (model columns use DateTime
    without timezone=True). Pydantic v2 serializes naive datetimes without
    a timezone offset. JavaScript parses such strings as local time, so
    every timestamp displayed to a user in a non-UTC timezone was offset
    by their UTC delta — 3 hours in Finland, 5 in New York, etc.
    
    Backend (schemas.py):
    - New TZAwareMixin with a wildcard field_serializer that attaches
      timezone.utc to naive datetime values during JSON serialization.
      Aware values pass through unchanged.
    - Applied to ItemResponse, MyWorkItem, MyWorkAssessment,
      MyWorkFinding. Every consumer of these responses now sees
      unambiguous UTC timestamps.
    - No model column changes, no migration. The underlying storage
      remains naive-UTC; only the wire format is corrected.
    
    Frontend (MyWorkView.tsx):
    - timeAgo() defensively appends 'Z' to naive ISO strings before
      constructing a Date. Belt-and-suspenders protection for any
      endpoint that hasn't yet adopted TZAwareMixin.
    
    Verified:
    - API now returns '2026-09-20T13:34:41.542793Z' for updated_at.
    - Editing an item and navigating to My Work shows 'just now'
      instead of '3h ago' for a user in UTC+3.
    - Other items in the list show timestamps matching their actual
      edit times, corrected by the UTC offset.
    
    Follow-up: other response schemas may still serialize naive
    datetimes without a Z suffix. Audit them and apply TZAwareMixin
    where needed. Not blocking, since the frontend defensive parse
    covers the display path.

    feat(traceboard): suspect-link workflow (backend)
    
    Classic RM workflow: when an item is edited after a relation is
    established, that relation becomes suspect until a reviewer
    explicitly clears it. Produces a governed audit trail that answers
    'was this change reviewed?' — a question the existing staleness
    metric could not.
    
    Design:
    - Suspicion is computed at read time from endpoint updated_at vs
      the reviewed timestamps. No background job, no event listener.
    - New relations are seeded as reviewed as of their endpoints'
      current state. Only subsequent edits flag them.
    - Legacy relations (pre-migration) are grandfathered with
      CURRENT_TIMESTAMP so nothing is retroactively flagged.
    - Two distinct metrics now coexist: stale_link_count (assessment-
      relative, existing) and suspect_link_count (managed workflow,
      new). They answer different questions and are not conflated.
    
    Model:
    - Relation gains source_reviewed_at, target_reviewed_at,
      reviewed_by, reviewed_at, review_note — all nullable.
    - New RelationReview model: append-only history table with FK to
      relations ON DELETE CASCADE.
    
    Migration tb0006_relation_suspect_state:
    - Adds the five columns.
    - Creates relation_reviews + index on relation_id.
    - Backfills existing relations with NOW() so they start non-suspect.
    
    Endpoints:
    - GET /items/{id}/trace/relations now returns suspect, reviewed_by,
      reviewed_at, review_note on each relation.
    - New POST /relations/{id}/review. Records the current endpoint
      timestamps as reviewed, captures reviewer/note, appends a
      relation_reviews row. Requires project member+.
    
    Write paths:
    - Relation creation (canonical API, seed, import, LLM generation)
      seeds the review timestamps from the endpoints' current
      updated_at, so new links start non-suspect.
    
    Engineering State:
    - compute_traceability_state now also emits suspect_link_count and
      suspect_links. Existing stale_link_* fields unchanged.
    
    Tests: 4 focused tests covering the full lifecycle, member-only
    review access, legacy-null conservative behavior, and Engineering
    State integration.

    - Baseline suspect: false.
